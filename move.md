## 1. Правовой контур — почему это не «на всякий случай»

| Норма | Что требует | Где нас касается |
|-------|-------------|------------------|
| **152-ФЗ, ст. 18 ч. 5** | БД с ПДн граждан РФ — физически на территории РФ | prod-VPS, PostgreSQL, MongoDB, бэкапы, логи в Loki (там ПДн после скраба?) |
| **152-ФЗ, ст. 12** | Трансграничная передача — уведомление РКН **до начала**, для США (не в перечне адекватной защиты) — только с письменного согласия субъекта | OpenAI (тексты дел!), Resend (email), Sentry SaaS, Google Fonts, HIBP |
| **152-ФЗ, ст. 10** | Спец. категории ПДн — усиленная защита | **Материалы юр. дел почти наверняка содержат спец. категории** (судимость, здоровье, нац. принадлежность) → УЗ-1/УЗ-2 |
| **Приказ ФСТЭК № 21** | Меры защиты для ИСПДн | аттестация площадки, СЗИ из реестра ФСТЭК |
| **ПП РФ № 1236** | Запрет закупки иностранного ПО для госзаказчиков | если целитесь в госюристов/ГУПы — нужны Postgres Pro, Angie, Axiom JDK из реестра ПО |
| **187-ФЗ (КИИ)** | Категорирование, ГосСОПКА | сама юрфирма — обычно не КИИ, но если среди клиентов банки/госорганы — вопрос всплывёт |
| **КоАП 13.11 (ред. 30.05.2025)** | Оборотные штрафы за утечку ПДн (до 3% выручки, от 20 млн ₽) | цена ошибки выросла на порядок |
| **63-ФЗ** | Квалифицированная ЭП | Диадок ✅ уже корректно |

**Главный юридический риск сейчас** — не CI/CD, а **отправка текстов юридических дел в OpenAI**.
Это трансграничная передача спец. категорий ПДн в страну без адекватной защиты, без согласия
субъектов (которыми являются в т.ч. третьи лица — контрагенты, свидетели). Это пункт №1 по приоритету.

## 2. 🔴 Критический уровень

### 2.1 OpenAI → российская LLM

**Где живёт:** `llm-service` (единственный шлюз, `llm.openai.*` в `application.yml`),
потребители в `ai-service`: RAG (`RagService`), `LegalDomainGuard`, `LlmReranker`,
`DocumentSummary`, `ContractReviewPrompt`, `TabularReviewPrompt`, `DraftRefinePrompt`,
`CaseAnalyticsPrompt`, `DocumentComparisonPrompt`.

**Хорошая новость:** архитектура уже готова к замене — `LlmClient` абстрагирован, `llm-service`
изолирован, `OPENAI_BASE_URL` вынесен в env. Менять надо один модуль, не весь `ai-service`.

**Варианты:**

| Провайдер | Модель / эмбеддинги | Плюсы | Минусы |
|-----------|--------------------|-------|--------|
| **Yandex Cloud AI Studio** | YandexGPT 5 Pro / `text-search-doc` (256 dim) | 152-ФЗ соответствие, ЦОД в РФ, ДПА, S3-совместимое хранилище рядом, аттестат ФСТЭК УЗ-1 | качество на длинных юр. текстах ниже gpt-4o; лимиты контекста |
| **GigaChat (Сбер)** | GigaChat 2 Max / `Embeddings` (1024 dim) | ЦОД РФ, есть реестровая версия, приемлемое качество на русском | API менее стабильно, жёсткая модерация промптов может резать юр. тематику |
| **Self-hosted** | Qwen3-32B / GigaChat-lite открытые веса + `bge-m3` (1024) на vLLM | **полный контроль, ПДн вообще не покидают контур**, нет квот и биллинга за токен | нужен GPU (A100/H100 или 2×4090), +200–400к ₽/мес или капзатраты |
| **MTS Cotype / T-Bank T-Pro** | — | РФ, растущее качество | меньше зрелости, меньше документации |

**Рекомендация:** гибрид — **YandexGPT как основной провайдер + self-hosted `bge-m3`
для эмбеддингов**. Причина: эмбеддинги — самый чувствительный поток (через них проходит
**весь корпус документов**, а не только вопрос), их дешевле всего увести на своё железо
(bge-m3 работает на CPU приемлемо, на одной 4090 — с запасом). Генерация ответа отправляет
наружу только top-K чанков — это меньший объём и его можно фильтровать.

**Что придётся сделать (это самая дорогая миграция):**

1. `LlmClient` → добавить реализации `YandexGptClient` / `GigaChatClient` рядом с `RemoteLlmClient`,
   выбор через `LLM_PROVIDER=openai|yandex|gigachat|local`.
2. **Аутентификация другая:** Yandex — IAM-токен с ротацией каждые 12 ч (не статичный Bearer);
   GigaChat — OAuth2 client_credentials + **обязательный российский корневой сертификат Минцифры
   в truststore JVM**. Это отдельная задача по образам (`docker/Dockerfile`: добавить
   `russian_trusted_root_ca.cer` в cacerts).
3. 🔥 **Смена размерности эмбеддингов ломает данные.** Сейчас `document_chunks.embedding vector(1536)`
   + HNSW-индекс. У bge-m3 / GigaChat — 1024, у Yandex — 256. Нужна Flyway-миграция с новой
   колонкой, **полная переиндексация всего корпуса** и период двойной записи. Планировать окно.
4. Перекалибровать `RAG_MAX_DISTANCE` (0.85 подобрано под `text-embedding-3-small`, для другой
   модели распределение косинусных расстояний иное — порог станет бессмысленным).
5. Перепроверить все промпты: `LegalDomainGuard`, реранкер и структурированный вывод
   (JSON-режим) ведут себя иначе. `RAG_RERANK_FAIL_OPEN=true` и `LLM_GUARD_FAIL_OPEN=false`
   в проде — на время миграции guard лучше не трогать.
6. Дневные квоты (`LLM_DAILY_QUOTA`, `LLM_DAILY_TOKEN_BUDGET`) — пересчитать под новый прайс.

**Промежуточный шаг на неделю** (если полная миграция не влезает в спринт): поднять
**российский OpenAI-совместимый прокси** (vLLM или Ollama с `/v1`-совместимым API) и просто
поменять `OPENAI_BASE_URL`. Код не трогается вообще. Качество упадёт, но юридическая дыра
закрывается сегодня, а не через квартал.

### 2.2 Resend → российский почтовый провайдер

**Где:** `user-service` — `ResendEmailClient`, `ResendProperties`,
`DeadlineNotificationEmailService`; env `RESEND_API_KEY`, `RESEND_FROM`,
`RESEND_MAX_EMAILS_PER_HOUR`. Используется для верификации email, сброса пароля,
инвайтов в организацию, напоминаний о дедлайнах.

| Замена | Комментарий |
|--------|-------------|
| **Unisender / Mailopost** | REST API, транзакционка, РФ, доступен в реестре ПО |
| **Sendsay** | РФ, транзакционка + маркетинг, хороший API |
| **SendPulse** | РФ-представительство, но юрлицо кипрское — проверять ДПА |
| **Яндекс 360 для бизнеса (SMTP)** | самый простой путь: обычный SMTP, `spring-boot-starter-mail` вместо HTTP-клиента |
| **Собственный Postfix + DKIM/SPF/DMARC** | максимум контроля, максимум возни с репутацией IP |

**Рекомендация:** **Unisender** (HTTP API — минимальная переделка `ResendEmailClient`,
сохраняется вся логика лимитов и ретраев) с **fallback на SMTP Яндекс 360**.

**Работы:** новый `EmailClient`-интерфейс + две реализации, `EMAIL_PROVIDER` в env,
перевыпуск SPF/DKIM/DMARC для `pravoos.ru`, прогрев домена. ~2–3 дня.

### 2.3 Cloudflare → российский CDN/WAF

**Где:** `docker/nginx/cloudflare-realip.conf`, `docker/nginx/cloudflare-origin-pull-ca.pem`,
`CF_ORIGIN_PULL` в `.env.example`, `scripts/lockdown-origin.sh` (ufw только с диапазонов CF),
раздел «Origin lockdown» в README.

**Что теряем при отключении CF:** DDoS-защита, WAF, TLS-терминация на edge, mTLS Authenticated
Origin Pull, скрытие IP origin. Это не «просто CDN» — это текущий периметр безопасности.

| Замена | Что закрывает |
|--------|--------------|
| **Qrator Labs** | anti-DDoS L3-L7 + WAF, лучший в РФ по L7, дорого |
| **StormWall / DDoS-Guard** | дешевле, anti-DDoS + WAF |
| **Ngenix** | CDN + WAF + anti-DDoS, реестр ПО, есть mTLS к origin |
| **Selectel CDN / VK Cloud CDN** | если хостинг уже там — дешевле и проще |
| **Yandex Cloud CDN + Smart Web Security** | WAF на базе правил, интеграция с Yandex ALB |

**Рекомендация:** **Ngenix** (или Qrator, если бюджет позволяет) — из-за поддержки
mTLS-подписи к origin, что позволяет сохранить текущую схему lockdown почти один-в-один.

**Работы:**
1. Заменить `cloudflare-realip.conf` на IP-диапазоны нового провайдера (`set_real_ip_from`).
2. Заменить `cloudflare-origin-pull-ca.pem` на CA нового провайдера, переписать
   `APP_GATEWAY_TRUSTED_PROXIES` (сейчас там приватные подсети + CF).
3. Переписать `scripts/lockdown-origin.sh` под новые диапазоны ufw.
4. **Обязательно: сменить IP origin у хостера.** В `memory/MEMORY.md` уже зафиксировано,
   что текущий IP **засвечен в git-истории** — при уходе с CF он становится прямой мишенью.
5. Перенести DNS: `reg.ru` / `Яндекс DNS` / DNS провайдера CDN.

### 2.4 Let's Encrypt → НУЦ Минцифры

**Где:** `docker-compose.prod.yml` (сервис `certbot`), `certbot_conf`/`certbot_www` volumes,
`ACME_EMAIL`, `scripts/deploy.sh` (выпуск SSL при bootstrap).

**Риск:** ISRG — американская НКО, подпадает под экспортные ограничения; прецеденты
отзыва сертификатов у российских доменов уже были.

**Замена:** **НУЦ Минцифры** — бесплатные TLS-сертификаты через Госуслуги, доверяются
Яндекс.Браузером, Atom и Chromium-Gost «из коробки». В Chrome/Firefox/Safari — **нет**,
пользователь увидит предупреждение.

**Практическая схема (не «или-или»):**
- Держать **оба** сертификата на nginx, отдавать по SNI/User-Agent — либо, проще:
  основной LE, а сертификат Минцифры лежит готовым в `docker/nginx/` и подключается
  одной переменной `TLS_PROVIDER=minc` при первых признаках проблем с ACME.
- Добавить в `scripts/deploy.sh` ветку выпуска/обновления через API Минцифры.
- Мониторинг срока действия — уже есть Prometheus, добавить `blackbox_exporter` с
  `probe_ssl_earliest_cert_expiry`.

### 2.5 GitHub / Actions / GHCR → российский CI/CD

**Где:** всё `.github/workflows/` (`ci.yml`, `_verify.yml`, `release.yml`, `rollback.yml`),
`.github/actions/setup-backend`, `.github/actions/ssh-deploy`, `docker-compose.images.yml`
(`ghcr.io/d3vy/pravoos`), `docker-bake.hcl`, `scripts/cicd/*`, Dependabot (пиннинг digest'ов
base-образов), Trivy (сканирование).

**Это самая объёмная миграция после LLM** — переписывается весь релизный конвейер.

| Замена | Плюсы | Минусы |
|--------|-------|--------|
| **Self-hosted GitLab CE + GitLab Runner + Harbor** | полный контроль, YAML близок к Actions по идеологии, всё в своём контуре | админить самому, ресурсы под сервер |
| **GitFlic** | реестр российского ПО, CI, registry, миграция репозиториев из GitHub встроенная | экосистема беднее, меньше готовых интеграций |
| **GitVerse (Сбер)** | активно развивается, бесплатно, CI есть | молодой, надёжность CI под вопросом |
| **Yandex Cloud (Managed GitLab + Container Registry)** | managed, не админить, рядом с хостингом | vendor lock-in в Яндекс |

**Рекомендация:** **self-hosted GitLab CE + Harbor** на отдельной VM у российского хостера.
Причина: у вас нетривиальный конвейер (bake-сборка 8 образов, ручной аппрув на прод,
smoke-тест, авто-откат, bash-тесты `scripts/cicd/tests/consistency.sh`) — на managed-решении
с ограниченным CI это придётся упрощать, а самописная логика уже отлажена.

**План переезда:**
1. Зеркало репозитория в GitLab (push-mirror из GitHub на переходный период).
2. `.gitlab-ci.yml`: перенести `_verify.yml` (mvn verify + фронт + bash-тесты) →
   job'ы `verify:backend`, `verify:frontend`, `verify:scripts`.
3. `docker/bake-action` → `docker buildx bake` напрямую в job'е с `docker:dind`.
   `docker-bake.hcl` остаётся без изменений.
4. `IMAGE_REGISTRY` → `registry.<домен>/pravoos` вместо `ghcr.io/d3vy/pravoos`.
   `docker-compose.images.yml` меняется одной переменной — тут архитектура помогла.
5. `ssh-deploy` action → `scripts/cicd/deploy-remote.sh` вызывается напрямую (он и так bash).
6. Ручной аппрув: GitLab `when: manual` + protected environment.
7. **Dependabot заменить** на `renovate` self-hosted (работает в GitLab CI) — иначе
   пиннинг base-образов по digest перестанет обновляться и это станет дырой в безопасности.
8. **Trivy**: бинарь свободный, но **БД уязвимостей тянется с ghcr.io**. Настроить
   `TRIVY_DB_REPOSITORY` на своё зеркало в Harbor + периодический sync.
   Альтернатива с российским вендором — сканер от **Positive Technologies (PT AI)** или
   **Solar appScreener** (оба в реестре, оба платные).

## 3. 🟠 Высокий уровень

### 3.1 MongoDB → PostgreSQL JSONB

**Где:** `ai-service`, БД `pravoos_chat` — только история чатов. Образ `mongo:7`.

MongoDB Inc. с 2022 не обслуживает российских клиентов; лицензия SSPL несовместима
с требованиями к свободному ПО у части заказчиков.

**Рекомендация: перенести чат в PostgreSQL (JSONB), а не искать «российский Mongo».**
Обоснование: коллекция одна, объём данных небольшой, паттерн доступа — «сообщения по
conversation_id, отсортированные по времени», это идеальный кейс для реляционки.
Уходит **целый контейнер, целое подключение, целый набор секретов** (`MONGO_USERNAME`/
`MONGO_PASSWORD` разбросаны по всем сервисам в `docker-compose.yml`) — чистый выигрыш
в сложности, а не только в импортозамещении.

Альтернативы, если Mongo-семантика реально нужна: **Tarantool** (VK, реестр ПО) или
**Picodata**. Обе потребуют переписать слой доступа целиком — дороже, чем JSONB.

**Работы:** Flyway-миграция `chat_conversations` + `chat_messages` (JSONB на метаданные),
переписать репозитории `@Document` → `@Entity`, скрипт разовой перекачки, удалить
`spring-boot-starter-data-mongodb`, вычистить `mongodb` из compose и `MONGO_*` из env.

### 3.2 ClamAV → Kaspersky Scan Engine

**Где:** сервис `clamav` в compose, `docker/clamav/clamd.conf`, `freshclam.conf`,
`CLAMAV_HOST/PORT/FAIL_OPEN`, `CLAMAV_MAX_SIGNATURE_AGE_DAYS=7`, интеграция в пайплайне
загрузки документов (fail-closed).

**Риск конкретный и недооценённый:** сам ClamAV — открытый код, но **базы сигнатур
качаются с `database.clamav.net` (Cisco, США)**. При отключении РФ freshclam перестанет
обновляться, а у вас `CLAMAV_MAX_SIGNATURE_AGE_DAYS=7` + `CLAMAV_FAIL_OPEN=false` →
**через неделю загрузка документов встанет полностью**. Это не гипотетический, а
запрограммированный отказ.

| Замена | Интеграция |
|--------|-----------|
| **Kaspersky Scan Engine** | ICAP или HTTP REST — ближе всего к текущей схеме «сервис по сети», реестр ПО, сертификат ФСТЭК |
| **Dr.Web ICAPD** | ICAP, реестр ПО, дешевле |

**Рекомендация:** **Kaspersky Scan Engine** по HTTP-режиму. Ваш `AntivirusScanner` уже
абстрагирован от протокола (сейчас говорит с clamd по TCP 3310) — меняется реализация клиента,
логика fail-closed / проверки свежести баз сохраняется как есть.

**Немедленный митигейт (сегодня, до миграции):** поднять внутреннее зеркало баз ClamAV
(`cvdupdate` тянет и складывает локально) и указать `DatabaseMirror` в `freshclam.conf`
на него. Это даёт запас времени.

### 3.3 Docker Hub → зеркало в Harbor / Yandex CR

**Что тянется из Docker Hub:** `pgvector/pgvector:pg16`, `mongo:7`, `redis:7-alpine`,
`confluentinc/cp-kafka:7.6.0`, `clamav/clamav:1.4`, `prom/prometheus`, `prom/alertmanager`,
`grafana/grafana`, `grafana/tempo`, `grafana/loki`, `grafana/alloy`, `nginx:alpine`,
`node:20-alpine`, `maven:3.9-eclipse-temurin-21`, `eclipse-temurin:21-jre-alpine`,
`certbot/certbot`.

Docker Hub уже блокировал РФ-адреса в 2022. Сейчас **прод собирается и деплоится
через доступ к Docker Hub — при блокировке встаёт и CI, и восстановление после сбоя.**

**Решение:** **Harbor** (или Nexus в режиме docker-proxy) как pull-through cache
рядом с GitLab. Все образы, включая базовые в `docker/Dockerfile` и `frontend/Dockerfile`,
переписываются на `registry.<домен>/proxy/...`. Digest-пиннинг сохраняется — это плюс,
он и защищает от подмены при зеркалировании.

Managed-альтернатива: **Yandex Container Registry** или **Selectel Container Registry**.

### 3.4 Maven Central / npm registry → Nexus proxy

`docker/Dockerfile` делает `mvn dependency:go-offline` и `mvn package`;
`frontend/Dockerfile` — `npm ci`. Обе цепочки идут в США.

**Решение:** тот же **Nexus Repository OSS** (он же может быть и docker-proxy из §3.3) —
три репозитория: `maven-proxy`, `npm-proxy`, `docker-proxy`. В образы прописать
`settings.xml` с `<mirror>` и `.npmrc` с `registry=`. Заодно ускорится сборка.

**Важно:** сделать периодический полный `pull` зависимостей в кеш (не полагаться на
lazy-proxy) — иначе при внезапной блокировке отсутствующий в кеше артефакт сломает сборку.

## 4. 🟡 Средний уровень

### 4.1 HIBP → локальная проверка паролей
`user-service/.../PasswordPolicyService.java`: `HIBP_BASE_URL = "https://api.pwnedpasswords.com"`
(k-anonymity, `hibp-fail-open: true`).

Утечки не происходит (k-anonymity отдаёт 5 символов SHA-1), но при блокировке проверка
молча выключается — `fail-open` превращает защиту в фикцию.

**Решение:** скачать дамп хешей HIBP (~10 ГБ, есть torrent/offline-выгрузка), залить топ-10M
самых частых в отдельную таблицу PostgreSQL с индексом по префиксу, реализовать
`LocalPwnedPasswordChecker`. Интерфейс тот же, `hibp-fail-open` становится не нужен.
Обновлять дамп раз в полгода вручную.

### 4.2 Sentry SaaS → GlitchTip self-hosted
В `README.md` уже указано «DSN совместим с self-hosted GlitchTip» — **работа фактически сделана**,
осталось поднять GlitchTip в compose и поменять `SENTRY_DSN` / `VITE_SENTRY_DSN` /
`SENTRY_INGEST_ORIGIN`. Не забыть убрать `https://*.sentry.io https://*.ingest.sentry.io`
из `connect-src` в `frontend/security-headers.conf`.
Самый дешёвый пункт списка после шрифтов.

### 4.3 Confluent cp-kafka → apache/kafka
`confluentinc/cp-kafka:7.6.0` — образ Confluent под **Community License** (не Apache 2.0),
с ограничениями на использование. Сам Kafka — Apache Foundation, проблем нет.
**Замена образа на `apache/kafka:3.7`** — конфигурация KRaft переносится почти дословно,
меняются префиксы части переменных. Полдня работы, снимает лицензионный вопрос.
Managed-альтернатива: **Yandex Managed Service for Apache Kafka**.

### 4.4 Redis → Valkey
Redis Ltd в 2024 сменил лицензию на RSALv2/SSPL. **Valkey** — форк под BSD от Linux Foundation,
**drop-in замена**: `image: valkey/valkey:8-alpine`, команда и healthcheck меняются
минимально (`valkey-server`, `valkey-cli`). Spring Data Redis работает без изменений.

### 4.5 nginx → Angie
**Angie** — форк nginx от бывшей российской команды разработчиков nginx, в реестре ПО,
конфиги совместимы. Меняется базовый образ во `frontend/Dockerfile` и в prod-nginx.
Нужен, если целитесь в госзаказчика; иначе можно отложить.

### 4.6 Eclipse Temurin → Axiom JDK
`docker/Dockerfile` собирает на `maven:3.9-eclipse-temurin-21` и рантаймит на
`eclipse-temurin:21-jre-alpine`. **Axiom JDK** (BellSoft) — российская сборка OpenJDK,
реестр ПО, сертификат ФСТЭК, есть Alpine-варианты. Замена базового образа + пересчёт digest.
Даёт формальное соответствие почти без работы.

### 4.7 Grafana-стек
Grafana Labs (США), Grafana/Loki с 2024 — AGPLv3. Для SaaS-продукта AGPL на инфраструктурном
инструменте (вы его не модифицируете и не распространяете) — приемлемо.
**Рекомендация: оставить, но зеркалировать образы (§3.3).** Если понадобится реестр ПО —
Yandex Monitoring или Zabbix + Grafana-совместимые дашборды. Приоритет низкий.

### 4.8 Web Push (VAPID) → RuStore Push + деградация
`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT`. VAPID — открытый стандарт,
но **фактическая доставка в Chrome идёт через FCM (Google)**, в Firefox — через Mozilla.
При блокировке FCM push в Chrome просто не дойдут — молча.

**Решение:** для мобильных — **RuStore Push SDK**; для веба — VAPID оставить, но
обязательно **достроить деградацию**: если push не подтверждён доставкой за N минут,
уведомление уходит в Telegram/email. Логика мультиканальной доставки уже
централизована (коммит `ee20246 refactor(notification)`) — встроить туда ещё один fallback дёшево.

### 4.9 Telegram → оставить + дублирующий канал
`api.telegram.org` используется в трёх местах: бот уведомлений (`notification-service`),
алерты Alertmanager (`TELEGRAM_ALERTS_CHAT_ID_*`), **доставка бэкапов**
(`scripts/backup.sh`: pg_dumpall + mongodump → GPG → Telegram).

Telegram — не российский (ОАЭ/Великобритания), но и не «уходящий»; в РФ работает,
хотя в 2025 были ограничения. Полный отказ сейчас не оправдан — юристы им пользуются.

**Что сделать обязательно:**
1. 🔥 **Убрать бэкапы из Telegram.** Отправка дампов БД с ПДн во внешний мессенджер —
   это трансграничная передача всей базы разом. Заменить на **S3-совместимое хранилище
   российского провайдера** (Yandex Object Storage / Selectel S3 / VK Cloud) с
   серверным шифрованием, версионированием и object lock. GPG-шифрование в скрипте оставить.
2. Алерты — продублировать в **email/webhook** на случай недоступности Telegram
   (алерты, которые не доходят, хуже отсутствия алертов).
3. Бот уведомлений — оставить, добавить **MAX (VK)** или SMS (SMS.ru / SMSC.ru)
   как альтернативный канал в уже существующей мультиканальной доставке.

## 8. Что архитектура уже сделала правильно

Стоит зафиксировать — это существенно снижает стоимость всей миграции:

- **`llm-service` как единственный шлюз к LLM.** Провайдер меняется в одном модуле,
  `ai-service` не трогается. Без этого миграция §2.1 была бы вдвое дороже.
- **`OPENAI_BASE_URL` вынесен в env** — временный митигейт через прокси делается без пересборки.
- **`IMAGE_REGISTRY` вынесен в переменную** в `docker-compose.images.yml` — уход с GHCR
  меняет одну строку в конфиге деплоя, а не восемь.
- **DSN Sentry совместим с GlitchTip** — миграция сводится к смене переменной.
- **`AntivirusScanner` абстрагирован** от clamd — замена на Kaspersky локальная.
- **Мультиканальная доставка уведомлений централизована** (коммит `ee20246`) —
  добавление MAX/SMS/email-fallback дёшево.
- **Интеграции выключаются пустым ключом** (`ARBITR_API_KEY`, `DIADOC_API_KEY`,
  `SENTRY_DSN`, `RESEND_API_KEY`) — можно мигрировать по одной, не ломая прод.
- **Base-образы пиннятся по digest** — при переезде на своё зеркало защита от подмены сохраняется.

## 9. Главный вывод

Проект **не находится в критической зависимости от иностранной инфраструктуры на уровне
архитектуры** — почти всё изолировано за интерфейсами и переменными окружения.
Зависимость сосредоточена в трёх местах, и они очень разные по цене:

1. **OpenAI** — дорого, долго, требует переиндексации данных. **И это единственный
   пункт с реальным юридическим риском прямо сейчас** (тексты дел уходят в США).
   Начинать с временного прокси, параллельно вести полную миграцию.
2. **GitHub/Actions/GHCR** — объёмно, но механически; риск в том, что при внезапной
   блокировке вы теряете возможность выкатить фикс. Это операционный, а не правовой риск.
3. **Cloudflare** — риск не в блокировке, а в том, что при уходе с CF **origin IP уже
   засвечен в git-истории**. Менять IP обязательно, одновременно с переездом.

Остальные 17 пунктов — от получаса до трёх дней каждый, и половина из них
(шрифты, GlitchTip, Valkey, apache/kafka, Axiom JDK) делается за одну неделю.

**Начните с волны 0.** За четыре дня работы вы закрываете утечку ПДн через шрифты,
перестаёте отправлять полные дампы базы в Telegram и предотвращаете запрограммированную
остановку загрузки документов через неделю после отключения ClamAV-зеркала.
